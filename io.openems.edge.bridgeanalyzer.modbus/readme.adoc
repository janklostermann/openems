= Modbus Bridge Analyzer

Implementation of the BridgeAnalyzer nature for Modbus/TCP and Modbus/RTU protocols.

== Overview

The Modbus Bridge Analyzer provides real-time inspection and debugging capabilities for Modbus communication in OpenEMS Edge. It captures protocol traffic between OpenEMS components and Modbus devices, exposing captured data through channels for visualization in the UI.

== Features

=== Phase 1 (Current)
* **Passive observation** - READ_ONLY mode with zero impact on communication
* **Protocol capture** - Record Modbus requests and responses
* **Packet decoding** - Parse function codes, register addresses, data values
* **Circular buffer** - Configurable packet history storage
* **Statistics** - Packet counts, buffer overruns, error rates
* **UI integration** - Real-time display of captured traffic

=== Future Phases
* **PASSTHROUGH mode** - Intercept and modify protocol traffic
* **SIMULATION mode** - Replace real devices with simulated responses
* **Advanced filtering** - Capture only specific function codes or addresses
* **Export capabilities** - Save captured data for offline analysis

=== Integration with Bridges

**Phase 1 Approach:**
The analyzer leverages the existing `LogVerbosity` mechanism in the Modbus bridge to capture traffic without modifying bridge code.

```
┌─────────────┐                                    ┌──────────────┐
│   Modbus    │ ──────registers protocol──────────►│    Modbus    │
│   Device    │                                     │    Bridge    │
│  Component  │                                     │              │
└─────────────┘                                     └──────┬───────┘
                                                           │
                                                           │ Logging events
                                                           │ (LogVerbosity)
                                                           ▼
                                                   ┌──────────────┐
                                                   │    Modbus    │
                                                   │   Analyzer   │
                                                   │              │
                                                   └──────────────┘
```

The analyzer:
1. Configures the bridge to use verbose logging
2. Subscribes to bridge logging events
3. Parses log messages to reconstruct Modbus packets
4. Stores packets in circular buffer
5. Exposes via BridgeAnalyzer channels

== Channels

=== From BridgeAnalyzer Nature

* `OPERATING_MODE` - Current mode (READ_ONLY)
* `CAPTURE_ENABLED` - Capture status
* `PACKETS_CAPTURED` - Total packet count
* `LAST_TRANSACTION` - Last captured packet (formatted)
* `BUFFER_OVERRUNS` - Buffer overflow count
* `ANALYZER_NOT_READY` - Warning state

=== Modbus-Specific Channels

* `LAST_FUNCTION_CODE` - Function code of last transaction (1-127)
* `LAST_REGISTER_ADDRESS` - Starting register address
* `LAST_REGISTER_COUNT` - Number of registers accessed
* `LAST_UNIT_ID` - Modbus unit/slave ID
* `LAST_TRANSACTION_TYPE` - READ or WRITE
* `LAST_ERROR_CODE` - Modbus exception code (if error)
* `MODBUS_ERRORS` - Count of Modbus protocol errors
* `TIMEOUT_ERRORS` - Count of timeout errors

== Usage Example

=== Configuration via Apache Felix Web Console

1. Navigate to OSGi → Configuration
2. Create new "BridgeAnalyzer Modbus" configuration
3. Set `bridge.id` to your Modbus bridge component ID (e.g., "modbus0")
4. Set `bufferSize` to desired packet history depth
5. Save configuration

=== Accessing Captured Data

==== Via OpenEMS UI
Navigate to the Analyzer view to see:
* Real-time packet capture
* Decoded Modbus messages
* Hex dump of raw data
* Statistics and error counts

==== Via JSON-RPC API
Query analyzer channels like any other component:

[source,json]
----
{
  "method": "getChannelValues",
  "params": {
    "componentId": "analyzer0",
    "channelIds": [
      "PACKETS_CAPTURED",
      "LAST_TRANSACTION",
      "LAST_FUNCTION_CODE"
    ]
  }
}
----

== Modbus Protocol Support

=== Supported Function Codes

**Read Operations:**
* `0x01` - Read Coils
* `0x02` - Read Discrete Inputs
* `0x03` - Read Holding Registers
* `0x04` - Read Input Registers

**Write Operations:**
* `0x05` - Write Single Coil
* `0x06` - Write Single Register
* `0x0F` - Write Multiple Coils
* `0x10` - Write Multiple Registers

**Diagnostic:**
* `0x17` - Read/Write Multiple Registers

=== Exception Handling

The analyzer captures and decodes Modbus exceptions:
* `0x01` - Illegal Function
* `0x02` - Illegal Data Address
* `0x03` - Illegal Data Value
* `0x04` - Slave Device Failure
* And all other standard exception codes

=== Transport Support

* **Modbus/TCP** - Via BridgeModbusTcp
* **Modbus/RTU** - Via BridgeModbusSerial

Both transports are supported transparently by referencing the appropriate bridge type.

== Performance Considerations

=== Memory Usage

With default buffer size of 100 packets:
* Average packet size: ~100 bytes
* Total buffer memory: ~10 KB
* Negligible impact on Edge systems

=== CPU Overhead

In READ_ONLY mode:
* Packet parsing: <1ms per packet
* String formatting: On-demand (when accessed)
* Expected overhead: <1% of cycle time

=== Thread Safety

The analyzer follows OpenEMS patterns:
* Respects process image (nextValue/value)
* Synchronized buffer access
* No blocking of bridge communication

== Troubleshooting

=== Analyzer Not Capturing

**Problem:** `PACKETS_CAPTURED` stays at zero

**Solutions:**
1. Verify `bridge.id` references correct bridge
2. Check bridge is actively communicating
3. Ensure `captureEnabled` is true
4. Check `ANALYZER_NOT_READY` state

=== Buffer Overruns

**Problem:** `BUFFER_OVERRUNS` increasing

**Solutions:**
1. Increase `bufferSize` configuration
2. Reduce capture verbosity (future feature)
3. Access captured data more frequently

=== High Memory Usage

**Problem:** Edge system memory pressure

**Solutions:**
1. Reduce `bufferSize`
2. Disable capture when not debugging (`captureEnabled=false`)
3. Reduce `maxPacketSize` if capturing large messages
