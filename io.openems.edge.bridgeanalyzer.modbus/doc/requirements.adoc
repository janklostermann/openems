= Modbus Bridge Analyzer Requirements

This document defines the requirements for the Modbus-specific implementation of the Bridge Analyzer.

== Stakeholders

=== System Integrator
Needs to debug Modbus communication issues in production environments without disrupting operation.

=== Developer
Needs to validate Modbus protocol implementation during device driver development.

=== Field Technician
Needs to verify correct Modbus communication during commissioning and troubleshooting.

=== OpenEMS System
Needs to maintain performance and stability while providing diagnostic capabilities.

== Functional Requirements

=== FR-1: Modbus Transaction Capture

**As a** system integrator +
**I want to** capture all Modbus transactions between OpenEMS and devices +
**So that** I can diagnose communication issues

==== FR-1.1: Request Capture
**Given** a Modbus bridge is performing read/write operations +
**When** a Modbus request is sent to a device +
**Then** the analyzer SHALL capture:
* Function code
* Unit ID (slave address)
* Starting register address
* Register count
* Write data (for write operations)
* Timestamp of request

**Test:** Send Modbus read request, verify all fields captured correctly

==== FR-1.2: Response Capture
**Given** a Modbus request has been sent +
**When** a response is received from the device +
**Then** the analyzer SHALL capture:
* Response data (for read operations)
* Exception code (if error response)
* Timestamp of response
* Transaction duration

**Test:** Receive Modbus response, verify all fields captured correctly

==== FR-1.3: Transport Independence
**Given** either a Modbus/TCP or Modbus/RTU bridge +
**When** transactions occur +
**Then** the analyzer SHALL capture transactions regardless of transport type

**Test:** Capture from both TCP and RTU bridges, verify identical behavior

=== FR-2: Data Exposure via Channels

**As a** user +
**I want to** access captured Modbus data through OpenEMS channels +
**So that** I can view it in the UI or access it via API

==== FR-2.1: Last Transaction Details
**Given** at least one transaction has been captured +
**When** querying analyzer channels +
**Then** the following channels SHALL contain data from the most recent transaction:
* `LAST_FUNCTION_CODE` - Integer (1-127)
* `LAST_REGISTER_ADDRESS` - Integer (0-65535)
* `LAST_REGISTER_COUNT` - Integer
* `LAST_UNIT_ID` - Integer (0-255)
* `LAST_TRANSACTION_TYPE` - String ("READ" or "WRITE")

**Test:** Execute transaction, read channels, verify values match transaction

==== FR-2.2: Error Information
**Given** a Modbus error has occurred +
**When** querying analyzer channels +
**Then** error information SHALL be available:
* `LAST_ERROR_CODE` - Integer (Modbus exception code, 0 if no error)
* `MODBUS_ERRORS` - Integer (cumulative count of protocol errors)
* `TIMEOUT_ERRORS` - Integer (cumulative count of timeouts)

**Test:** Trigger Modbus exception, verify error channels updated

==== FR-2.3: Formatted Transaction Display
**Given** at least one transaction has been captured +
**When** reading the `LAST_TRANSACTION` channel +
**Then** it SHALL contain a human-readable string including:
* Transaction type (Read/Write)
* Function code with name
* Unit ID
* Register address and count
* Hex dump of data
* Error information (if applicable)

**Test:** Capture transaction, verify formatted string contains all elements

==== FR-2.4: Capture Statistics
**Given** the analyzer is operating +
**When** querying statistics channels +
**Then** the following SHALL be available:
* `PACKETS_CAPTURED` - Total transactions captured since activation
* `BUFFER_OVERRUNS` - Count of lost transactions due to buffer full

**Test:** Capture multiple transactions, verify counts are accurate

=== FR-3: Bridge Reference

**As a** system integrator +
**I want to** specify which Modbus bridge to analyze +
**So that** I can monitor specific communication paths

==== FR-3.1: Bridge Configuration
**Given** a Modbus bridge component exists with ID "modbus0" +
**When** configuring the analyzer with `bridge.id = "modbus0"` +
**Then** the analyzer SHALL capture transactions from that bridge only

**Test:** Configure analyzer with bridge ID, verify only that bridge's traffic is captured

==== FR-3.2: Invalid Bridge Handling
**Given** the configured bridge ID does not exist +
**When** the analyzer activates +
**Then** the analyzer SHALL:
* Set `ANALYZER_NOT_READY` state channel to WARNING
* Log an error message
* Not capture any transactions

**Test:** Configure non-existent bridge ID, verify NOT_READY state and no capture

==== FR-3.3: Bridge Independence
**Given** the analyzer is capturing from a bridge +
**When** the bridge performs normal operations +
**Then** the bridge's behavior SHALL NOT be affected:
* No additional latency in Modbus communication
* No failed transactions due to analyzer
* No change in bridge error handling

**Test:** Measure bridge performance with/without analyzer, verify < 2% difference

=== FR-4: Capture Control

**As a** user +
**I want to** enable and disable packet capture +
**So that** I can control when diagnostic data is collected

==== FR-4.1: Enable Capture
**Given** capture is disabled (`captureEnabled = false`) +
**When** setting `captureEnabled = true` +
**Then** the analyzer SHALL:
* Begin capturing new transactions
* Update `CAPTURE_ENABLED` channel to true
* Increment `PACKETS_CAPTURED` for each new transaction

**Test:** Enable capture, perform transactions, verify capture occurs

==== FR-4.2: Disable Capture
**Given** capture is enabled +
**When** setting `captureEnabled = false` +
**Then** the analyzer SHALL:
* Stop capturing new transactions
* Update `CAPTURE_ENABLED` channel to false
* NOT increment `PACKETS_CAPTURED`
* Retain existing buffer contents

**Test:** Disable capture, perform transactions, verify no new captures

=== FR-5: Operating Mode

**As a** system administrator +
**I want to** ensure the analyzer operates in read-only mode +
**So that** it cannot interfere with production communication

==== FR-5.1: Read-Only Mode
**Given** the analyzer is active +
**When** checking the `OPERATING_MODE` channel +
**Then** it SHALL return "READ_ONLY"

**Test:** Query operating mode, verify returns "READ_ONLY"

==== FR-5.2: Passive Operation
**Given** the analyzer is in READ_ONLY mode +
**When** Modbus transactions occur +
**Then** the analyzer SHALL NOT:
* Modify request data
* Modify response data
* Inject additional transactions
* Block or delay transactions

**Test:** 
* Monitor Modbus traffic with protocol analyzer, verify no modifications, 
* Do a code review to ensure no modification logic is reachable in this mode

== Non-Functional Requirements

=== NFR-1: Performance

==== NFR-1.1: Minimal Latency Impact
**Given** the analyzer is capturing transactions +
**When** measuring end-to-end Modbus transaction time +
**Then** the overhead SHALL be < 2% compared to operation without analyzer

**Test:** Benchmark 1000 transactions with/without analyzer, verify < 2% overhead

==== NFR-1.2: No Blocking
**Given** the analyzer buffer is full +
**When** new transactions occur +
**Then** transactions SHALL NOT be blocked or delayed

**Test:** Fill buffer, continue transactions, verify no blocking

==== NFR-1.3: Cycle Time Impact
**Given** the analyzer is operating in an OpenEMS cycle +
**When** measuring cycle execution time +
**Then** the analyzer SHALL add < 1ms to the cycle time

**Test:** Measure cycle time with/without analyzer over 1000 cycles

=== NFR-2: Resource Usage

==== NFR-2.1: Memory Bounds
**Given** the analyzer is configured with `bufferSize = N` packets +
**When** capturing transactions +
**Then** total memory usage SHALL NOT exceed:
* N × maxPacketSize × 2 bytes (for packet data)
* Plus 10KB overhead (for structures)

**Test:** Configure buffer=100, maxPacket=512, monitor memory, verify < 110KB

==== NFR-2.2: No Memory Leaks
**Given** the analyzer has been running for 24 hours +
**When** measuring memory usage +
**Then** memory SHALL remain constant (within 5% variance)

**Test:** Run for 24h with continuous traffic, verify stable memory

==== NFR-2.3: Buffer Configuration Range
**Given** configuring the buffer size +
**When** setting `bufferSize` parameter +
**Then** valid range SHALL be 10 to 1000 packets

**Test:** Configure buffer=10 (accept), buffer=1000 (accept), buffer=5 (reject)

=== NFR-3: Reliability

==== NFR-3.1: Thread Safety
**Given** multiple threads accessing analyzer channels +
**When** concurrent reads and captures occur +
**Then** NO data corruption or race conditions SHALL occur

**Test:** Multi-threaded stress test with concurrent capture and channel reads

==== NFR-3.2: Exception Handling
**Given** an error occurs during packet capture +
**When** the error is encountered +
**Then** the analyzer SHALL:
* Log the error
* Continue operating for subsequent transactions
* NOT crash or deactivate

**Test:** Inject malformed packet data, verify analyzer continues

==== NFR-3.3: Circular Buffer Behavior
**Given** the buffer contains `bufferSize` packets and is full +
**When** a new packet is captured +
**Then** the analyzer SHALL:
* Evict the oldest packet
* Store the new packet
* Increment `BUFFER_OVERRUNS` counter

**Test:** Fill buffer, add one more, verify oldest removed and counter incremented

=== NFR-4: Compatibility

==== NFR-4.1: Modbus Function Code Support
**Given** a Modbus device uses standard function codes +
**When** capturing transactions +
**Then** the analyzer SHALL correctly decode:
* 0x01 - Read Coils
* 0x02 - Read Discrete Inputs
* 0x03 - Read Holding Registers
* 0x04 - Read Input Registers
* 0x05 - Write Single Coil
* 0x06 - Write Single Register
* 0x0F - Write Multiple Coils
* 0x10 - Write Multiple Registers
* 0x17 - Read/Write Multiple Registers

**Test:** Execute each function code, verify correct decoding

==== NFR-4.2: Exception Code Support
**Given** a Modbus device returns an exception +
**When** capturing the error response +
**Then** the analyzer SHALL correctly decode exception codes:
* 0x01 - Illegal Function
* 0x02 - Illegal Data Address
* 0x03 - Illegal Data Value
* 0x04 - Slave Device Failure
* And all other standard codes (0x05-0x0B)

**Test:** Trigger each exception type, verify correct decoding

==== NFR-4.3: OSGi Lifecycle Compliance
**Given** the analyzer is an OSGi component +
**When** component lifecycle events occur +
**Then** the analyzer SHALL:
* Activate successfully when configuration is valid
* Deactivate cleanly, releasing resources
* Handle configuration updates without restart (when possible)

**Test:** Activate, deactivate, modify config, verify proper lifecycle handling

=== NFR-5: Usability

==== NFR-5.1: Configuration Simplicity
**Given** a user wants to add an analyzer +
**When** configuring via UI or JSON +
**Then** only the following parameters SHALL be required:
* `id` - component ID
* `bridge.id` - reference to Modbus bridge

All other parameters SHALL have sensible defaults.

**Test:** Create analyzer with minimal config, verify it activates and works

==== NFR-5.2: Readable Output
**Given** a user views the `LAST_TRANSACTION` channel +
**When** reading the formatted string +
**Then** it SHALL be understandable without consulting documentation

**Test:** User study or review of formatted output readability

== Configuration Requirements

=== CFR-1: Required Parameters
The analyzer SHALL require the following configuration parameters:
* `id` - String - Unique component identifier
* `bridge.id` - String - ID of the Modbus bridge to analyze

**Test:** Attempt activation without these parameters, verify failure

=== CFR-2: Optional Parameters with Defaults
The analyzer SHALL support the following optional parameters:
* `alias` - String - Default: "" - Human-readable name
* `enabled` - Boolean - Default: true - Component enable state
* `captureEnabled` - Boolean - Default: true - Capture enable state
* `bufferSize` - Integer - Default: 100 - Packet buffer size (10-1000)
* `maxPacketSize` - Integer - Default: 512 - Max bytes per packet (64-2048)

**Test:** Create analyzer without optional params, verify defaults applied

== Constraints

=== Constraint 1: No Bridge Modification
**The analyzer SHALL NOT require** modifications to existing Modbus bridge code. All capture mechanisms must work with bridges as they currently exist.

**Rationale:** Minimize risk, enable faster delivery, maintain backward compatibility.

=== Constraint 2: Phase 1 Limitations
**The analyzer SHALL NOT implement** in Phase 1:
* PASSTHROUGH mode (packet modification)
* SIMULATION mode (virtual device)
* Packet filtering by criteria
* Export to file
* Historical packet storage beyond buffer

**Rationale:** Focused scope for initial delivery, reduce complexity.

=== Constraint 3: OpenEMS Patterns
**The analyzer SHALL follow** OpenEMS architectural patterns:
* Process image pattern for channel updates
* Component lifecycle (activate/deactivate)
* Configuration via @ObjectClassDefinition
* Nature-based interface design

**Rationale:** Consistency with OpenEMS ecosystem, maintainability.

== Out of Scope

The following are explicitly **NOT** requirements for Phase 1:
* Packet modification capabilities
* Device simulation
* Advanced filtering (by function code, address range, etc.)
* Statistical analysis
* Packet export to files
* Custom UI widgets
* Real-time packet streaming

== Success Criteria

The implementation SHALL be considered successful when:

1. **All functional requirements are met** - verified through tests
2. **All NFRs are met** - verified through performance and stress tests
3. **Zero impact on bridge operation** - verified through integration tests
4. **Memory usage within bounds** - verified through long-running tests
5. **Thread-safe operation** - verified through concurrent access tests
6. **Code follows OpenEMS standards** - verified through code review
7. **Documentation complete** - JavaDoc, integration guide, examples
