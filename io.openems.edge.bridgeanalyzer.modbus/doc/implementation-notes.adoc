= Modbus Analyzer Implementation Notes

This document provides technical implementation details for developers working on the Modbus Analyzer.

== Architecture Decisions

=== What Belongs in analyzer.api vs. analyzer.modbus

==== analyzer.api (Protocol-Agnostic)

**Nature: BridgeAnalyzer**
* `OPERATING_MODE` channel - All analyzers have modes
* `CAPTURE_ENABLED` channel - All analyzers can enable/disable capture
* `PACKETS_CAPTURED` channel - All analyzers count packets
* `LAST_TRANSACTION` channel - All analyzers show last transaction (formatted)
* `BUFFER_OVERRUNS` channel - All analyzers have bounded buffers
* `ANALYZER_NOT_READY` state - All analyzers can be misconfigured

**Enum: OperatingMode**
* READ_ONLY - Universal concept
* PASSTHROUGH - Universal concept
* SIMULATION - Universal concept

**Abstract classes (future):**
* `AbstractPacketBuffer<T>` - Generic circular buffer
* `AbstractPacketFormatter` - Protocol-specific formatting contract

==== analyzer.modbus (Modbus-Specific)

**Nature: ModbusAnalyzer** (extends BridgeAnalyzer)
* `LAST_FUNCTION_CODE` channel - Modbus concept
* `LAST_REGISTER_ADDRESS` channel - Modbus registers
* `LAST_REGISTER_COUNT` channel - Modbus batch operations
* `LAST_UNIT_ID` channel - Modbus addressing
* `LAST_TRANSACTION_TYPE` channel - Could be generic, but Modbus READ/WRITE
* `LAST_ERROR_CODE` channel - Modbus exception codes
* `MODBUS_ERRORS` channel - Protocol-specific errors
* `TIMEOUT_ERRORS` channel - Could be generic, but Modbus-common issue

**Classes:**
* `ModbusPacket` - Modbus-specific packet structure
* `PacketBuffer` - Implementation of circular buffer for ModbusPacket
* `ModbusPacketFormatter` - Modbus protocol formatting
* `ModbusAnalyzerImpl` - OSGi component implementation

**Enums:**
* `ModbusFunctionCode` - Modbus function codes
* `ModbusTransactionType` - READ, WRITE
* `ModbusExceptionCode` - Modbus exception codes

=== Phase 1 Implementation Strategy

==== Capture Mechanism Options

**Option A: Bridge Logging Hook** _(Recommended for Phase 1)_

Leverage existing `LogVerbosity` in Modbus bridge:

```java
// In ModbusAnalyzerImpl
@Reference
protected ConfigurationAdmin configurationAdmin;

@Activate
void activate(Config config) {
    // Get bridge configuration
    var bridgeConfig = this.configurationAdmin.getConfiguration(
        "Bridge.Modbus.Tcp", config.bridge_id());

    // Set bridge to verbose logging
    var props = bridgeConfig.getProperties();
    props.put("logVerbosity", "READS_AND_WRITES_VERBOSE");
    bridgeConfig.update(props);

    // Subscribe to log events from bridge
    // Parse log output to reconstruct packets
}
```

**Pros:**
* No bridge modification required
* Works immediately with existing bridges
* Safe and non-invasive

**Cons:**
* Relies on log message format (fragile)
* May miss some packet details
* Performance overhead of string parsing

**Option B: Bridge Event Listener** _(Phase 1.5 if needed)_

Add listener interface to bridge:

```java
// In bridge.modbus.api
public interface ModbusCommunicationListener {
    void onRequest(ModbusRequest request);
    void onResponse(ModbusResponse response);
    void onError(ModbusException exception);
}

// Bridge implementation
private final List<ModbusCommunicationListener> listeners = ...;

void executeRequest(ModbusRequest request) {
    notifyListeners(l -> l.onRequest(request));
    var response = doActualCommunication(request);
    notifyListeners(l -> l.onResponse(response));
}
```

**Pros:**
* Clean, typed packet access
* No string parsing
* Better performance

**Cons:**
* Requires bridge modification
* Need PR to bridge.modbus first
* Phase 1 blocker

**Decision:** Start with Option A, migrate to Option B if performance/reliability insufficient.

==== Channel Update Pattern

```java
@Override
public void handleEvent(Event event) {
    switch (event.getTopic()) {
    case EdgeEventConstants.TOPIC_CYCLE_BEFORE_PROCESS_IMAGE:
        // Update channels from buffer before process image
        updateChannelsFromBuffer();
        break;
    }
}

private void updateChannelsFromBuffer() {
    var lastPacket = this.packetBuffer.getLast();
    if (lastPacket != null) {
        this._setLastTransaction(lastPacket.toFormattedString());
        this._setLastFunctionCode(lastPacket.getFunctionCode().getValue());
        this._setLastRegisterAddress(lastPacket.getStartAddress());
        // ... other channels
    }

    this._setPacketsCaptured(this.packetBuffer.size());
    this._setBufferOverruns(this.packetBuffer.getOverrunCount());
}
```

== Component Lifecycle

=== Activation Sequence

```java
@Activate
void activate(ComponentContext context, Config config) {
    super.activate(context, config.id(), config.alias(), config.enabled());

    // 1. Initialize packet buffer
    this.packetBuffer = new PacketBuffer(config.bufferSize());

    // 2. Validate bridge reference
    if (!validateBridgeReference(config.bridge_id())) {
        this._setAnalyzerNotReady(true);
        this.logWarn(this.log, "Bridge not found: " + config.bridge_id());
        return;
    }

    // 3. Set up capture mechanism
    if (config.captureEnabled()) {
        enableCapture(config.bridge_id());
    }

    // 4. Set initial channel values
    this._setOperatingMode(OperatingMode.READ_ONLY.getName());
    this._setCaptureEnabled(config.captureEnabled());
    this._setAnalyzerNotReady(false);
}
```

=== Modification Handling

```java
@Modified
void modified(ComponentContext context, Config config) {
    super.modified(context, config.id(), config.alias(), config.enabled());

    // Handle buffer size change
    if (config.bufferSize() != this.packetBuffer.getMaxSize()) {
        this.packetBuffer = new PacketBuffer(config.bufferSize());
    }

    // Handle capture enable/disable
    if (config.captureEnabled() != this.captureEnabled) {
        if (config.captureEnabled()) {
            enableCapture(config.bridge_id());
        } else {
            disableCapture(config.bridge_id());
        }
        this.captureEnabled = config.captureEnabled();
        this._setCaptureEnabled(config.captureEnabled());
    }
}
```

=== Deactivation Cleanup

```java
@Deactivate
protected void deactivate() {
    // Disable capture
    disableCapture(this.currentBridgeId);

    // Clear buffer
    this.packetBuffer.clear();

    super.deactivate();
}
```

== Thread Safety Considerations

=== Concurrent Access Patterns

```java
// Buffer access is synchronized
public synchronized void add(ModbusPacket packet) { ... }

// Channel updates happen in cycle event
@Override
public void handleEvent(Event event) {
    // Only update channels during BEFORE_PROCESS_IMAGE
    // This ensures thread safety per OpenEMS pattern
}

// Configuration changes synchronized
@Modified
synchronized void modified(...) { ... }
```

=== Lock Ordering

To avoid deadlocks:
1. Always acquire buffer lock before channel updates
2. Never hold buffer lock when calling bridge methods
3. Release all locks before returning from event handlers

== Memory Management

=== Packet Size Estimation

```
Typical ModbusPacket size:
- Timestamp: 16 bytes
- Primitive fields: 32 bytes
- Byte arrays (max): 2 * maxPacketSize
- Total: ~48 bytes + 2*maxPacketSize

With maxPacketSize=512:
- Per packet: ~1 KB
- Buffer of 100: ~100 KB
- Acceptable for Edge systems
```

== Open Questions

1. **Should PacketBuffer be generic in analyzer.api?**
   - Pro: Reusable across protocols
   - Con: Each protocol has different packet structure
   - Decision: Defer to Phase 1 completion, evaluate pattern

2. **Should LAST_TRANSACTION be String or structured?**
   - Pro (String): Simple, protocol-agnostic
   - Con (String): UI must parse for display
   - Pro (Structured): Type-safe, easier UI consumption
   - Decision: String for Phase 1, consider JSON in future

3. **How to handle extremely high traffic?**
   - Could add sampling (capture every Nth packet)
   - Could add filtering (only errors, only specific FCs)
   - Decision: Monitor performance in Phase 1, add if needed

4. **Should analyzer be a bridge itself?**
   - Would allow true passthrough architecture
   - Major refactoring of existing patterns
   - Decision: No for Phase 1, reconsider for Phase 2
