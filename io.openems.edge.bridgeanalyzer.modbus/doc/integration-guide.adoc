= Modbus Analyzer Integration Guide

This guide explains how to integrate the Modbus Analyzer into your OpenEMS Edge system for debugging and monitoring Modbus communication.

== Prerequisites

* OpenEMS Edge installation
* At least one configured Modbus bridge (TCP or RTU)
* Modbus device components communicating via the bridge
* Access to Apache Felix Web Console or OpenEMS UI

== Integration Scenarios

=== Scenario 1: Debugging Communication Issues

**Situation:** A Modbus device is showing intermittent communication errors.

**Integration Steps:**

1. **Identify the bridge** - Determine which bridge component the problematic device uses:
   - Open Felix Web Console → OSGi → Configuration
   - Find your device component configuration
   - Note the `modbus.id` parameter (e.g., "modbus0")

2. **Create analyzer** - Add a new analyzer component:
   - Configuration → Factory Configurations
   - Click "BridgeAnalyzer Modbus"
   - Set:
     * `id`: "analyzer0" (or unique name)
     * `bridge.id`: "modbus0" (from step 1)
     * `bufferSize`: 100
     * `captureEnabled`: true
   - Save

3. **Monitor traffic** - Open OpenEMS UI:
   - Navigate to System → Analyzer
   - Select "analyzer0"
   - Watch real-time packet capture

4. **Analyze errors** - Look for:
   - Modbus exception codes in responses
   - Timeout patterns
   - Invalid register addresses
   - Checksum failures (RTU)

5. **Export findings** - Copy relevant packet data for support tickets

6. **Disable when done** - To save resources:
   - Set `captureEnabled`: false
   - Or delete analyzer configuration

=== Scenario 2: Validating New Device Implementation

**Situation:** Developing a new Modbus device component, need to verify protocol correctness.

**Integration Steps:**

1. **Set up test environment:**
   ```
   Device Component (under development)
        ↓
   Modbus Analyzer (capture all traffic)
        ↓
   Modbus Bridge (TCP/RTU)
        ↓
   Test Device or Simulator
   ```

2. **Configure analyzer with large buffer:**
   - `bufferSize`: 500 (capture more history)
   - `captureEnabled`: true

3. **Exercise all device functions:**
   - Read all registers
   - Write test values
   - Trigger edge cases
   - Test error handling

4. **Verify against specification:**
   - Compare captured packets with device datasheet
   - Verify register addresses
   - Check data types and byte order
   - Validate function codes

5. **Check for protocol violations:**
   - Invalid function codes
   - Out-of-range addresses
   - Incorrect data lengths

=== Scenario 3: Production Monitoring

**Situation:** Want passive monitoring of critical device without performance impact.

**Integration Steps:**

1. **Configure minimal analyzer:**
   - `bufferSize`: 10 (only recent packets)
   - `captureEnabled`: false (enable only when needed)

2. **Create monitoring dashboard:**
   - Add analyzer channels to UI
   - Monitor `MODBUS_ERRORS` count
   - Alert on `TIMEOUT_ERRORS` increase

3. **Enable capture on-demand:**
   - When issue suspected, set `captureEnabled`: true via API
   - Capture a few minutes of traffic
   - Analyze, then disable

== Configuration Patterns

=== Minimal Configuration (Production)

[source,properties]
----
id=analyzer0
alias=Production Monitor
enabled=true
bridge.id=modbus0
bufferSize=10
captureEnabled=false
operatingMode=READ_ONLY
----

**Use case:** Monitoring with minimal overhead, enable capture only when troubleshooting.

=== Development Configuration

[source,properties]
----
id=analyzer_dev
alias=Development Analyzer
enabled=true
bridge.id=modbus_test
bufferSize=500
captureEnabled=true
operatingMode=READ_ONLY
maxPacketSize=1024
----

**Use case:** Full capture during development and testing.

=== Multiple Analyzers

You can run multiple analyzers simultaneously:

[source,properties]
----
# Analyzer for production bridge
id=analyzer_prod
bridge.id=modbus0
bufferSize=10
captureEnabled=false

# Analyzer for test bridge
id=analyzer_test
bridge.id=modbus1
bufferSize=500
captureEnabled=true
----

**Use case:** Monitor multiple Modbus networks independently.

== UI Integration

=== Accessing Analyzer Data

**Method 1: OpenEMS UI Component View**
1. Navigate to: Edge → <Your Edge> → System → Components
2. Find "analyzer0" in component list
3. Click to view all channels

**Method 2: Custom Analyzer View** _(if available)_
1. Navigate to: Edge → <Your Edge> → Analyzer
2. Select analyzer from dropdown
3. View formatted packet list

=== Understanding Packet Display

**Typical packet display format:**
```
[2025-11-22 14:30:15.123] READ  Unit:1  FC:03  Addr:1000  Count:10  → OK (20 bytes)
[2025-11-22 14:30:15.145] WRITE Unit:1  FC:06  Addr:2000  Value:1234 → OK
[2025-11-22 14:30:15.167] READ  Unit:1  FC:04  Addr:5000  Count:5   → ERROR (Exception 02)
```

**Field explanations:**
* **Timestamp** - Exact time of transaction
* **Type** - READ or WRITE operation
* **Unit** - Modbus unit/slave ID (1-247)
* **FC** - Function code (hex)
* **Addr** - Starting register/coil address
* **Count** - Number of registers/coils
* **Value** - Data written (for writes)
* **Result** - OK, ERROR, or TIMEOUT

=== Hex Dump View

For detailed analysis, view raw packet data:

```
Request:  01 03 03 E8 00 0A C5 F1
          ^  ^  ^^^^^ ^^^^^ ^^^^^
          |  |    |     |     +-- CRC (RTU only)
          |  |    |     +-------- Count (10 registers)
          |  |    +-------------- Address (0x03E8 = 1000)
          |  +------------------- Function Code (0x03 = Read Holding)
          +---------------------- Unit ID (1)

Response: 01 03 14 00 01 00 02 ... AB CD
          ^  ^  ^  ^^^^^^^^^^^^^... ^^^^^
          |  |  |        |            +-- CRC (RTU only)
          |  |  |        +--------------- Data (20 bytes = 10 registers)
          |  |  +------------------------ Byte count (20)
          |  +--------------------------- Function Code (0x03)
          +------------------------------ Unit ID (1)
```

== JSON-RPC API Integration

=== Querying Analyzer Channels

**Get all analyzer channels:**
[source,json]
----
{
  "jsonrpc": "2.0",
  "method": "getEdge",
  "params": {
    "edgeId": "edge0"
  },
  "id": 1
}
// Response includes analyzer0 component with all channels
----

**Get specific channels:**
[source,json]
----
{
  "jsonrpc": "2.0",
  "method": "queryHistoricTimeseriesData",
  "params": {
    "timezone": "Europe/Berlin",
    "fromDate": "2025-11-22T00:00:00Z",
    "toDate": "2025-11-22T23:59:59Z",
    "channels": {
      "analyzer0/PacketsCaptured": {},
      "analyzer0/ModbusErrors": {},
      "analyzer0/TimeoutErrors": {}
    }
  },
  "id": 2
}
----

=== Controlling Analyzer

**Enable capture:**
[source,json]
----
{
  "jsonrpc": "2.0",
  "method": "updateComponentConfig",
  "params": {
    "componentId": "analyzer0",
    "properties": [
      {
        "name": "captureEnabled",
        "value": true
      }
    ]
  },
  "id": 3
}
----

== Performance Impact Analysis

=== Measuring Overhead

1. **Baseline measurement** (analyzer disabled):
   - Note cycle time from `_cycle/CycleTime` channel
   - Monitor for 1 hour
   - Calculate average

2. **With analyzer** (capture enabled):
   - Enable analyzer
   - Monitor cycle time for 1 hour
   - Calculate average

3. **Compare:**
   - Expected overhead: <1%
   - If higher, reduce `bufferSize` or disable

=== Optimization Tips

**Reduce overhead:**
* Disable capture when not needed (`captureEnabled=false`)
* Reduce `bufferSize` to minimum required
* Use smaller `maxPacketSize` if possible

**Increase capture depth:**
* Increase `bufferSize` (memory permitting)
* Monitor `BUFFER_OVERRUNS` channel
* If overruns occur, increase buffer or reduce traffic

== Common Integration Issues

=== Issue: Analyzer shows ANALYZER_NOT_READY

**Causes:**
1. Bridge ID not found
2. Bridge not active
3. Analyzer configuration incomplete

**Solution:**
```bash
# Check bridge exists
# Via Felix Console → OSGi → Components
# Search for component with ID matching bridge.id

# Verify bridge is active
# Status should be "ACTIVE" not "UNSATISFIED"

# Check analyzer configuration
# All required parameters set
```

=== Issue: PACKETS_CAPTURED not increasing

**Causes:**
1. `captureEnabled` is false
2. Bridge has no active communication
3. Device components not polling

**Solution:**
```bash
# Enable capture
captureEnabled=true

# Verify bridge is communicating
# Check bridge channels show data updates

# Verify device components active
# At least one device should reference this bridge
```

=== Issue: High BUFFER_OVERRUNS count

**Causes:**
1. Buffer too small for traffic volume
2. Packets not being consumed/cleared

**Solution:**
```bash
# Increase buffer
bufferSize=500  # or higher

# Check UI is polling analyzer
# Ensure frontend is reading LastTransaction channel

# Consider reducing capture rate (future feature)
```

== Best Practices

=== Development Phase
* Use large buffer (500+)
* Keep capture always enabled
* Monitor all Modbus-specific channels
* Export packet logs for documentation

=== Testing Phase
* Medium buffer (100-200)
* Enable capture for test duration
* Focus on error channels
* Compare against expected behavior

=== Production Phase
* Small buffer (10-50)
* Capture disabled by default
* Enable only during troubleshooting
* Alert on error thresholds

=== Security Considerations

* **Access control** - Restrict analyzer configuration to authorized users
* **Sensitive data** - Analyzer captures all Modbus traffic, may include sensitive values
* **Resource limits** - Large buffers can impact memory on constrained devices
* **Logging** - Do not enable detailed logging in production (security risk)

== Example: Complete Integration Workflow

**Goal:** Debug intermittent read errors on Carlo Gavazzi energy meter.

**Steps:**

1. **Identify configuration:**
   ```
   Device: meter0 (Carlo Gavazzi EM24)
   Bridge: modbus0 (TCP, 192.168.1.100:502)
   Issue: Occasional read timeouts
   ```

2. **Create analyzer:**
   ```
   id: analyzer_em24
   bridge.id: modbus0
   bufferSize: 200
   captureEnabled: true
   ```

3. **Monitor for 1 hour:**
   - Watch `TIMEOUT_ERRORS` channel
   - Note timestamps of errors
   - Review `LAST_TRANSACTION` during errors

4. **Analyze findings:**
   ```
   Pattern: Timeouts occur every ~30 minutes
   Correlation: During high grid power (>10kW)
   Hypothesis: Meter response delayed under load
   ```

5. **Adjust configuration:**
   - Increase Modbus timeout in bridge config
   - Reduce polling frequency for this device
   - Test with analyzer still enabled

6. **Verify fix:**
   - Monitor for another hour
   - `TIMEOUT_ERRORS` should stop increasing
   - Disable analyzer capture

7. **Document:**
   - Save packet examples
   - Note timeout values that worked
   - Update device readme with findings
