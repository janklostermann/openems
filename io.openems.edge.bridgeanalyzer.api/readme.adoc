= Bridge Analyzer API

The Bridge Analyzer API provides nature definitions for protocol bridge analyzers in OpenEMS Edge.

== Purpose

Bridge analyzers are diagnostic and debugging components that intercept communication between OpenEMS components and hardware devices across various communication bridges (Modbus, HTTP, M-Bus, OneWire). They enable:

* **Protocol inspection** - Real-time visibility into raw protocol traffic
* **Debugging assistance** - Capture and analyze communication issues
* **Development support** - Validate device implementations
* **Testing capabilities** - Simulate device behavior without hardware

== Architecture Concept

=== Analyzer as Transparent Proxy

Bridge analyzers act as transparent intermediaries between OpenEMS components and communication bridges:

```
┌─────────────────┐         ┌──────────────────┐         ┌──────────────┐         ┌────────────┐
│  OpenEMS        │ ◄─────► │  Bridge Analyzer │ ◄─────► │    Bridge    │ ◄─────► │   Device   │
│  Component      │ Protocol│  (Intercepts)    │ Protocol│  (Modbus/    │  Wire   │  Hardware  │
│  (e.g., Meter)  │         │                  │         │   HTTP/etc.) │         │            │
└─────────────────┘         └──────────────────┘         └──────────────┘         └────────────┘
                                     │
                                     │ Exposes captured data
                                     │ via Channels
                                     ▼
                             ┌────────────────┐
                             │   OpenEMS UI   │
                             │  (Debugging)   │
                             └────────────────┘
```

=== Nature Definition

The `BridgeAnalyzer` nature defines the common interface that all protocol-specific analyzer implementations must provide:

* **Operating modes** - READ_ONLY, PASSTHROUGH, SIMULATION
* **Capture control** - Enable/disable packet capture
* **Statistics** - Packet counts, buffer overruns
* **Data access** - Last transaction, captured packets

== Operating Modes

=== READ_ONLY Mode
Passive observation mode that does not interfere with normal operation:

* Captures protocol traffic in real-time
* No modification of data
* Minimal performance impact
* Safe for production environments

=== PASSTHROUGH Mode _(Future)_
Active interception with optional modification:

* All READ_ONLY capabilities
* Ability to modify requests/responses
* Inject delays for timing tests
* Useful for testing error handling

=== SIMULATION Mode _(Future)_
Replace real device with simulated responses:

* Emulate device behavior
* Test without hardware
* Reproduce specific scenarios
* Training and demonstration purposes

== Channel Definitions

The BridgeAnalyzer nature provides these standard channels:

|===
| Channel | Type | Description

| `OPERATING_MODE`
| String
| Current operating mode (READ_ONLY, PASSTHROUGH, SIMULATION)

| `CAPTURE_ENABLED`
| Boolean
| Whether packet capture is currently enabled

| `PACKETS_CAPTURED`
| Integer
| Total number of packets captured since activation

| `LAST_TRANSACTION`
| String
| Raw data of last captured transaction (protocol-specific format)

| `BUFFER_OVERRUNS`
| Integer
| Number of times capture buffer was full (data lost)

| `ANALYZER_NOT_READY`
| State
| Warning state when analyzer is not properly configured
|===

== Protocol-Specific Implementations

Each communication bridge type has its own analyzer implementation:

* **io.openems.edge.analyzer.modbus** - Modbus/TCP and Modbus/RTU analyzer
* **io.openems.edge.analyzer.http** _(Future)_ - HTTP bridge analyzer
* **io.openems.edge.analyzer.mbus** _(Future)_ - M-Bus analyzer
* **io.openems.edge.analyzer.onewire** _(Future)_ - OneWire analyzer

Each implementation extends the base `BridgeAnalyzer` nature with protocol-specific channels and functionality.

== Integration Pattern

To use a bridge analyzer:

1. **Configure analyzer component** - Set up the analyzer for your protocol (e.g., Modbus)
2. **Connect to bridge** - Analyzer references the actual bridge component
3. **Connect devices to analyzer** - Device components reference the analyzer instead of the bridge directly
4. **Access captured data** - Use OpenEMS UI or API to view captured protocol traffic

Example configuration flow:
```
Modbus Device Component → references → Modbus Analyzer → references → Modbus Bridge → Hardware
```

== Use Cases

=== Field Installation Debugging
Technicians can enable an analyzer in production to diagnose communication issues without modifying the actual component configuration.

=== Development & Testing
Developers can validate protocol implementations by inspecting raw traffic and comparing against device specifications.

=== Educational Purposes
Training environments can demonstrate how devices communicate at the protocol level.

=== Automated Testing
Test suites can verify correct protocol behavior by analyzing captured transactions.

== Design Principles

=== Protocol Independence
The BridgeAnalyzer nature is protocol-agnostic. Protocol-specific details are handled by implementations.

=== Non-Invasive
Analyzers should not affect normal system operation in READ_ONLY mode. They observe but do not interfere.

=== Performance Conscious
Capturing and buffering should be optimized to minimize impact on cycle timing and memory usage.

=== Thread-Safe
Analyzers must respect OpenEMS's process image pattern and cycle synchronization.
