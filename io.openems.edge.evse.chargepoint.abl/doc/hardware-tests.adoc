= ABL eMH1 — Hardware Validation Test Suite
:toc:
:toc-placement: preamble

Hardware test procedures for `io.openems.edge.evse.chargepoint.abl`.
These tests validate behaviour that cannot be covered by unit tests alone — they require a
physical ABL eMH1 device connected via RS-485/Modbus-ASCII.

Status legend: *PASS* — observed to work. *FAIL* — bug found. *OPEN* — not yet run. *SKIP* — not applicable to this hardware variant.

---

== Prerequisites

=== Required Hardware

* ABL eMH1 wallbox (any supported product variant — see test notes per case)
* RS-485 USB adapter connected to the eMH1 RS-485 terminals
* EV or CP/PP load simulator (a 1 kΩ resistor between CP and PE simulates an EV connected but not drawing current (IEC 61851 State B); close switch via 270 Ω to simulate draw State C)
* Multimeter or clamp meter (for fault-injection scenarios)
* Laptop running OpenEMS edge with `evseChargePoint0` using this driver

=== Software Setup

. Build and deploy `io.openems.edge.evse.chargepoint.abl` and the ASCII bridge bundle.
. Configure the component:
+
[source]
----
id = evseChargePoint0
modbus_id = modbus0 (BridgeModbusSerialAscii, ablCompatible = true)
modbusUnitId = 1
hardwareType = <match your physical unit>
fallbackVoltageL1/L2/L3 = 230
enableUpstreamTimeout = true     (default)
readOnly = false                  (for write tests — set true for H01d)
logVerbosity = READS_AND_WRITES_VERBOSE
----
. Open OpenEMS REST/JSON API or CLI debug view to observe channel values in real time.
. If you have a Modbus packet sniffer (e.g. `modpoll`, Wireshark on the USB serial adapter), use it to capture raw frames independently. The bridge logs every ASCII frame when `logVerbosity = READS_AND_WRITES_VERBOSE`.

=== Notation

* *Reg `0xABCD`* — Modbus holding register at that address (decimal equivalent noted where helpful).
* *FC3* — Read Holding Registers.
* *FC10 / FC16* — Write Multiple Registers (ABL eMH1 requires FC16; FC6 produces corrupt frames).
* *Frame shown as:* `:UUFFAAAALLDDRR[LRC]CRLF` or `>01...` (ABL response, `>` replaces `:` — handled transparently by the bridge).
* *Channel* refers to an OpenEMS channel on component `evseChargePoint0`.

== H01  STARTUP OUTLET ENABLE  (behaviour goal G4a — HYPOTHESIS)

_Validates: on activation, the driver writes `0xE2E2` to reg `0x0005` when device is in A1 or E0, enabling the outlet._

=== H01a — Normal startup from A1 (no EV)

*Precondition:* No EV cable connected; device in state A1; outlet previously enabled.

*Steps:*

. Confirm `EVSE_STATE = A1` via channel read.

== H04  UPSTREAM TIMEOUT CONFIGURATION  (behaviour goal G9 — HYPOTHESIS)

_Validates: reg `0x002C` write arms the hardware watchdog; when OpenEMS goes silent the device raises F4._

=== H04a — Startup writes 0x9001 to reg 0x002C

*Precondition:* `enableUpstreamTimeout = true` (default); `readOnly = false`; device in A1.

*Steps:*

. Restart OpenEMS component.
. Observe log.

*Expected sequence in log (order matters):*

. `DEBUG WRITE: :011000050001...E2E2[LRC]` (reg `0x0005`, outlet enable).

*Verify:* The `0x002C` write fires only when device is in state E2 (precondition per spec). If device starts in B2/C2, no `0x002C` write should appear — test H04b covers that edge case.

=== H04d — Upstream timeout counter reset mechanism (open question U4)

_Determines whether FC3 reads alone reset the timeout counter, or only writes to reg `0x0005`._

*Precondition:* Upstream timeout enabled. Device in A1 (no EV, for safety). Timeout interval known.

*Steps (reads-only scenario):*

. Confirm OpenEMS is polling normally (FC3 reads every 1 s, no writes — e.g. setpoint unchanged).
. Wait 1.5× the timeout interval without any write operation.
. Observe: does the device raise F4?

*Expected A (reads reset counter — spec assumption):* No F4; device stays in A1. +
*Expected B (only writes reset counter):* F4 is raised after timeout.

*If Expected B:* A periodic keepalive write to reg `0x0005` (`0xE2E2`, roughly every 30 s) must be added to the driver.

*Resolves open question U4.*
